## Activation is source-locked OFF for this release
`CLOUD_RELEASE_APPROVED` is checked in as false. Cloud progress stays OFF even if an existing build environment sets `VITE_CLOUD_SYNC_ENABLED=true`. Activation requires a separately reviewed code change to the lock AND exact public flag `true`. Enabled-cloud browser tests use a test-only Vite module alias; production has no query parameter, local-storage switch or runtime bypass. Missing/false/malformed values use account-scoped local-only progress, with a persistent UI warning and account/legacy exports. No progress RPC is constructed in that mode. This is not a runtime fallback: enabled cloud errors remain fail-closed and never switch to local-only mode.

Do not enable the flag before the reviewed migration, stable backend, recoverable backup/restore verification and separate release approval. No live configuration was changed. Changing the source lock and rebuilding with the flag enabled is feature activation. Once activated with real data, turning it back off forks local/cloud histories: do not use the flag as an automatic rollback. Preserve/export both and use an approved reconciliation plan. Local-only journals are offered as explicit owner-confirmed imports into EMPTY cloud accounts; existing cloud data is never auto-replaced.

Missing public Supabase configuration leaves authentication unavailable; it does not enable cloud or silently identify a guest as another user. Password recovery stays outside progress hydration in either mode.

# Per-account cloud progress — rollout gate

## Model and boundaries
The authenticated Supabase account owns one versioned progress document. A new device hydrates from the server before any defaults are written. Local edits form a durable account-specific journal, and coupled chore/progress changes are committed in one transaction after a short batching delay. A captured owner-token client prevents global account changes from retargeting an old request.

Writes use expected-version CAS and UUID idempotency receipts. A lost response retries the same operation. Concurrent devices cannot silently overwrite each other; conflict UI preserves/export both copies and offers explicit cloud-copy adoption. It does not merge or overwrite the cloud reward ledger. One tab at a time may write each account, enforced with Web Locks; unsupported browsers fail closed. A blocked/corrupt/full storage journal never silently becomes an in-memory-only queue.

Synced: chores, allowance, custom templates, simulation stats/achievements, profile, learning/simulated investment/savings/spending progress, onboarding choices, theme and colors. Audio/device preferences remain local. Authentication tokens, database connection strings, bank/brokerage credentials and real financial balances are never in the sync allowlist.

Chore occurrences have stable identities. Undo does not retract earned historical progress and re-completion does not award again. PostgreSQL enforces monotonic occurrence IDs and count increments only for new IDs; the whole snapshot (including completion state and simulated rewards) commits atomically. XP/achievement/learning logic remains app simulation, not a server-authoritative real-money ledger or proof a chore was physically done. Lesson completion is not a newly designed exact-once rewards ledger.

## Existing data
Old shared-browser and prior account-scoped data are not silently uploaded or deleted. Empty cloud accounts offer an explicit preview and ownership-confirmed import; malformed fields stay in the original store and are excluded with a warning. Existing cloud accounts are never replaced by legacy import. Imported money is unverified simulation state. Export remains available. The existing live `public.chores` table is not migrated/copied automatically into this new document; verify whether it contains real data with an authorized, owner-aware migration before rollout.

## Recovery and retained exposure
For a failed application rollout, revert the application release first; retain the new tables/receipts and exports instead of dropping user progress. Restore/import procedures require an approved backup and owner mapping. The migration is additive; no existing tables/data are deleted.

Tracked `.env` is removed in this branch. Existing Git history and previously deployed artifacts may still contain old values; deleting the file or making the repository private does not revoke credentials. Rotation and artifact/history response remain separately authorized tasks. Never test suspected exposed credentials.

## Test scope caveats
Browser tests mock auth/RPC and block non-local HTTP(S); database tests use actual PostgreSQL roles/JWT claims but are not the production Supabase gateway. Neither proves current email delivery, production login, live RLS deployment, real banking, real brokerage, all device/browser behavior, or cloud billing/availability. Do not describe these as “everything tested.”
